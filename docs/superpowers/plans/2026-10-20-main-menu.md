# Main menu implementation plan

**Goal:** Implement the approved main-menu design with flight setup, multiplayer, shared settings, hardware information, recording access, help, quit and repeatable return navigation.

**Architecture:** A dedicated, lightweight `MainMenu` scene uses uGUI/TextMeshPro and shared in-flight settings presenters. A session coordinator transfers validated launch configuration into the existing `Multiplayer` scene and delegates startup to `RoleSelectionUI`; solo initially uses a local host. Gameplay remains authoritative and the menu never instantiates a helicopter or NOVA controller.

**Baseline:** `6a948a9`, with existing dirty multiplayer, camera, input and test work. Preserve all existing edits. Work in place because the current Editor and uncommitted integration form the required baseline. No commits or package upgrades authorized.

## Constraints and review

- Unity `6000.4.5f1`, NGO `2.11.2`, Input System `1.19.0`, uGUI `2.0.0`, OpenXR `1.15.1`; preserve package lock.
- One Unity operator: lead. Agents must not operate Unity, tests, builds or serialized assets.
- Risk: high for connection/return lifecycle; medium for UI/settings. Independent preimplementation and integrated review covers lifecycle, absent hardware, local/remote authority, settings drafts and navigation.
- No platform movement, live motion tuning, physics simplification, invented locations/aircraft, vendor SDKs or cloud matchmaking.
- Preserve existing in-flight overlay behaviour and saved preference meanings.

## Acceptance and failure cases

- Launch into a readable menu; keyboard/mouse navigation works without HOTAS/HMD/NOVA.
- Quick Start repeats a valid setup; the catalogue contains only the built gameplay scene and supported aircraft/activity. Invalid saved options fall back safely.
- Host/join retains pilot/spectator roles, endpoint validation, connection feedback, retries and cancel. Clients never apply host-owned world setup.
- Settings work before helicopter spawn; saved display/binding/general/Cesium values are shared with gameplay. Dirty navigation offers Apply/Discard/Cancel; failed validation keeps drafts and focus.
- Menu scene contains no simulation, network startup or motion-output components. Hardware status never treats a local component as proof of physical connection.
- Returning saves active recordings through existing writers before teardown, awaits network shutdown, destroys only session-owned persistent objects, and restores a usable menu. Repeat launch/return without duplicate managers or stale callbacks.
- Loading failure or unavailable scene restores controls with an actionable message; duplicate starts are blocked.
- A headset is optional; desktop settings must not overwrite tracked HMD transforms. Validate readable seated-VR presentation separately.
